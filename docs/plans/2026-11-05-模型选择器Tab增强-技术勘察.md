# 模型选择器 Tab 增强 —— 技术勘察

> 目的：在动手前把 DSH 的模型选择器契约、竞品生态、可行路径与硬约束记录清楚。
> 结论未定稿，等待决策项（见文末）。

## 一、需求原话

- 作用于模型选择器的增强
- 按提供商分 Tab，再加模型子 Tab
- 减少长列表时滚动翻找的耗时与视觉分散
- Provider ID 作为提供商 Tab 的分类键
- 模型名前缀（如 `deepseek-flash` → `deepseek`）作为模型子 Tab 的分类键

## 二、DSH 侧契约（已实测，非推测）

### 2.1 槽位

| 项 | 值 |
|---|---|
| 槽名 | `conversation.input.model` |
| kind | `single` |
| scope | `session` |
| 默认占用者 | `@deepseek-ai/dsh-client-ui-model-selection` 的 `ModelSelect` |
| 声明方 | `client-ui-conversation` 中 `conversation.composer.bar` 的某个 entry |
| ownerProps | `{ locked: boolean }` |
| 子槽 | `conversation.input.model.label`（`single` / `session` / `inline`） |

### 2.2 single 槽的渲染规则（源码实证）

`SlotCore.register` 对 `kind: "single"`：

- 同优先级重复注册 → **抛错**
- 不同优先级 → 允许，`entriesOfSlot` 按 priority **升序**返回，`SlotOutlet` 取 `entriesOfSlot(key)[0]`

即：**单槽同一时刻只有一个 entry 会渲染**，`priority` 越小越先。官方原生注册在 `priority: 0`，插件注册 `priority: -1` 即可遮蔽。

> 原文（`SlotCore.register`）：`single slot "..." already has a registration at priority N ... — register at a different priority to shadow it (lowest renders)`

**关键推论：single 槽是"替换"语义，不存在"部分接管"。** 无法只替换模型列表、把其它部分留给别的插件。

### 2.3 原生 UI 结构（`ModelSelect`）

已是两级菜单，`type Pane = 'root' | 'model' | 'effort'`：

```
root    : [「模型」行 → drill] [「推理等级」行 → drill]
model   : 搜索框(模型数>4才出现) + provider 分组列表(MenuGroup + sticky 头) + 状态/错误/重试
effort  : 推理档位列表(读 model.reasoning.efforts)
```

原生**已按 provider 分组**，顺序：`deepseek-account` → `deepseek-official` → 其它按目录序。
原生**已有搜索**：大小写不敏感的有序子序列匹配，组内前缀优先 → 对齐分 → 目录序。

数据面：`modelDirectories.directoryFor(sessionId).store`，snapshot 含
`{ current, routable, groups: [{id, name, models}], failures, status, pending, error }`，
提交走 `directory.select({ provider, model, reasoningEffort? })`。

### 2.4 `/model` 斜杠命令无法接管

走 `commandUi` 的 `popupSelect`，由 `client-ui-commands` 自己渲染。
插件没有注入点。生态内竞品（`dsh-liao-models`）踩过：全局 CSS 会误伤它，因为两者共用
`MenuGroup` 原语（`section[role="group"]`）。

**结论**：Tab 增强只能作用于 composer 的模型按钮，`/model` 维持官方原样。

## 四、生态现状（竞品调研结论）

抓取 8 个市场索引，去重后 **14,056 个插件**：

- 简介涉及"模型选择器/菜单/下拉" → **187 个**
- 做 provider/渠道分组 → **19 个**
- 已做到"系列/家族"二级 → **4 个**（`dsh-model-cascade`、`dsh-model-navigator`、`dsh-model-hub-2`、`dsh-liao-models`）
- **以 Tab 作为主信息架构 → 0 个**

最接近的三个：

| 插件 | 形态 | 与本需求的重合点 |
|---|---|---|
| `dsh-model-cascade` | 三级级联：供应商 → 系列 → 模型 | 完全覆盖"provider + 族"；族切分自认会裂 |
| `dsh-model-navigator` | 供应商 + 家族两级折叠，搜索/收藏/最近 | 同上，另有"一键恢复官方"开关 |
| `dsh-model-picker-plus` | 双行标签栏：视图（推荐/最近/收藏/全部）+ 厂商标签 | 唯一用标签栏，但本质是 provider 平铺 + 视图过滤 |

**官方动向**：仓库 `has_issues=false`、`has_pull_requests=false`（只能走 Discussions，无相关提案）。
`ui-model-selection` 近一周提交全是浮层定位修复（CSS Anchor Positioning / 移动端边界 / 吸顶毛玻璃），
**无分组、Tab、搜索增强的功能性工作**。官方 README 明写 `THERE WILL BE COMPATIBILITY-BREAKING CHANGES`。

**战略含义**：
1. 需求真实，但已是红海（19 个同向插件），"做个 Tab" 不足以构成差异化。
2. "模型名前缀族"本身不新；**没人做出稳定、可配置的族定义** → 这是可防御点。
3. 所有竞品都放弃 `/model` → 必须显式声明范围，并给"一键恢复官方"。
4. 竞品普遍依赖 `priority: -1` 遮蔽，而官方刚大改浮层定位 → 护城河在"宿主升级自检 + 挂载前退让"。

### 5.1 与 reasoning-effort 的共存，技术上是不可行的（重要）

reasoning-effort 的机制：

```js
const entry = ctx.slots.entries(SLOT).find(e =>
  e.locale === "model" && e.children?.["conversation.input.model.label"] !== void 0)
entry.component = wrapNativeSelector(original, panel)   // 只装饰"原生 entry"
```

它是**装饰原生 entry**，不是注册新 entry。而 single 槽只渲染 `priority` 最小的那一个：

- 我们注册 `priority: -1` → **我们渲染，原生 entry 不再渲染** → 它装饰的那个组件根本不上屏
- 它的 `mapNativeTree` 还硬性要求菜单树形如：`aria-label === t("menu.aria")` 且 root 恰好 3 个 children
  → 我们的 Tab 结构不会匹配，即使被找到也只是静默 no-op

**因此：路径 A（整体替换槽）必然让 reasoning-effort 的滑块失效。**
"只接管模型列表、effort 面板交还给它"这个组合在 single 槽语义下不成立 —— 我此前给出的该选项判断有误，特此更正。
